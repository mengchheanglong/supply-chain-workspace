What needs to change in osm-pathfinder?
Its current capabilities—Dijkstra, A*, Contraction Hierarchies, OSM road parsing, and time-dependent routing—give us a useful starting point.

But for enterprise distribution, I'd extend it with:

Distance/time matrix API — efficiently calculate costs between hundreds or thousands of delivery stops.

Vehicle profiles — motorcycles, vans, trucks, with appropriate road access and restrictions.

Route constraints — closures, turn restrictions, vehicle restrictions, and supported traffic conditions.

Route validation — test route correctness against known paths and full OSM datasets, not only demo graphs.

Versioned routing data — ensure simulations can reproduce results using the same road-network version.

We should also compare its routing accuracy and performance with established engines such as OSRM and Valhalla before relying on it for actual business decisions.

One important boundary: osm-pathfinder determines travel costs and road paths. A separate optimization service, potentially using Google OR-Tools, decides which vehicles serve which deliveries and in what order.

So the division remains:

supply-chain-platform  → manages operations
logistics-sandbox      → simulates operations
distribution-intelligence → optimizes decisions
osm-pathfinder         → calculates road routes
My recommendation is to keep the existing osm-pathfinder repository, improve it incrementally, and expose it as a reusable routing service.

That way, each project strengthens the others without becoming tightly coupled.

One important networking detail
Inside Docker, services should communicate using Compose service names rather than localhost.

For example:

From Windows:
http://localhost:3000  → osm-pathfinder

From logistics-sandbox container:
http://routing:3000    → osm-pathfinder
Your current logistics-sandbox routing and e-commerce clients use hardcoded localhost defaults. Those should become configurable environment variables.

Your Rust routing server also defaults to binding to 127.0.0.1; inside its container, it needs to bind to 0.0.0.0 to accept requests from other containers.

Don't start every database every time
This is especially important because your original e-commerce architecture includes Cassandra, Neo4j, Hive, and HDFS.

I'd introduce Docker Compose profiles:

Docker officially supports selectively enabling optional services through profiles.

A few rules I would establish
Keep each application independently buildable and runnable.

Give each database its own persistent Docker volume.

Use health checks so services wait for dependencies to become ready.

Maintain separate development and production configurations.

Never connect sandbox test data to production databases with write permissions.

Put the parent workspace under Git separately, without accidentally committing nested repositories or database volumes.

depends_on with service_healthy can help coordinate startup after databases become healthy.
